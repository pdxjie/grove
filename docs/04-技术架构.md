# 04 技术架构

> 核心判断：**"卡"是数据架构问题，不是 UI 框架问题。**
> 先用可量化的性能预算约束架构，再选框架。

---

## 1. 技术选型

### 1.1 三个候选

| 维度 | SwiftUI 原生 | Tauri 2 + Rust + Web | Electron |
|------|--------------|----------------------|----------|
| 启动/内存 | 最优 | 好（WKWebView 常驻 ~80MB） | 差（Chromium 常驻 200MB+） |
| 大列表/Diff 渲染 | 需自绘，成本高 | Canvas/DOM 虚拟化成熟 | 同左，但更重 |
| macOS 原生质感 | 原生 | 需插件模拟（材质、菜单） | 需大量模拟 |
| 开发效率 | 低（无热更新、预览受限） | 高（HMR） | 高 |
| 现有代码复用 | 0 | 可复用 `source_tree` 的 Rust 内核；UI 参考 `rill` 的 React + Tailwind 体系 | 0 |
| 本机工具链 | **仅 CLT，无 Xcode** | Rust 1.97 + Node 24 就绪 | 就绪 |
| 跨平台 | 仅 Apple | 三平台 | 三平台 |
| 分发体积 | ~5MB | ~15–25MB | ~120MB+ |

### 1.2 结论：Tauri 2 + Rust 内核 + React 19 / TypeScript

**理由（按权重）**

1. **可立即开工**：本机没有完整 Xcode（`xcode-select` 指向 CommandLineTools，SDK 15.2），SwiftUI 路线要先装 ~10GB Xcode，且 Swift 生态里没有成熟的 Git 解析/三方合并库。
2. **内核可复用**：`source_tree` 已有 435 行 `git.rs` + 173 行 `rebase.rs` + 262 行 `commands.rs`，验证过"调系统 git CLI"的路线。
3. **性能可控**：真正的热点（git 调用、日志解析、图布局、diff 计算、语法高亮）全部放 Rust；WebView 只做绘制，配合虚拟化与 Canvas 足够 60fps。
4. **跨平台期权**：Tauri 天然支持 Windows/Linux，v1 只发 macOS，但不必为移植重写。
5. **审美不受限**：CSS 的设计自由度高于 SwiftUI，且能精确还原设计稿；UI 直接沿用 `rill` 已验证的暗色设计体系（炭黑 + 橙红强调、13px 紧凑排版、12px 圆角）。
6. **与 rill 同栈**：React 19 + Tailwind 3 + zustand + lucide，组件与交互可直接借鉴，减少重复造轮子。

**风险与对冲**

| 风险 | 对冲 |
|------|------|
| WKWebView 内存/长列表 | DOM 节点预算 < 2000；图用 Canvas；diff 用虚拟滚动 |
| 不够"原生" | 自绘窗口控件 + `window-vibrancy` 材质 + 原生菜单/托盘/快捷键 |
| 大文件 diff 卡主线程 | Rust 计算 + 分页返回 + 前端只渲染可视区 |

**何时应改选 SwiftUI**：如果最终目标是"极致原生手感 + 只做 Mac + 愿意投入 3 个月学习"，SwiftUI + libgit2 是更纯粹的答案。但以当前工具链与时间预算，Tauri 是唯一能在 10 周内产出可用版本的路径。

│  ├─ components: GraphCanvas / DiffView / FileTree / Chips     │

│  ├─ graph/     lane 布局、增量计算                              │
│  ├─ diff/      Myers/Patience、词级、tree-sitter 高亮           │
│  ├─ ops/       commit/merge/rebase/cherry-pick/stash/worktree  │
│  ├─ conflict/  三方合并、结构化 resolver、状态机                │

│  ├─ watch/     fsevents 去抖、增量失效                          │
│  └─ store/     内存 LRU、磁盘缓存、设置                         │

**关键约束**：前端**不得**直接执行 git；所有能力以类型化命令暴露。这样内核可被 CLI/测试/未来的 SwiftUI 外壳复用。

## 3. Git 内核策略：CLI 为主，库为辅

### 3.1 为什么是系统 git CLI

- 自动继承：credential helper（Keychain）、`~/.gitconfig`、别名、hooks、GPG 签名、LFS、`core.autocrlf`、子模块配置。
- 行为与用户终端一致，不会出现"GUI 能提交、CLI 报错"的错位。
- 复杂操作（rebase、merge、worktree）的边界情况，CLI 已经处理了 15 年。

### 3.2 何时用库

| 场景 | 方案 | 理由 |
|------|------|------|
| 读 log / 读对象 / 解析 tree | `gix`（gitoxide）快路径，失败回退 CLI | 避免进程启动开销（~10ms/次，页面渲染要调几十次） |
| diff 计算 | `similar` crate（Rust） | 需要在内存里做词级/结构级二次 diff |
| 三方合并 | `git merge-file --diff3 -p` 或自实现 | 复用 git 的冲突标记语义 |
| 写操作 | **永远 CLI** | 钩子、锁、签名、凭据必须走官方路径 |
| 语法高亮 | `tree-sitter` + 语法包 | 纯计算，放 Rust |

### 3.3 命令封装规范

- 参数数组传递，**绝不拼 shell 字符串**（防注入、防路径空格问题）。
- 统一设置：`-c core.quotepath=false -c color.ui=false --no-pager`。
- 统一 locale：`LC_ALL=C`（解析稳定），错误信息再本地化。
- 每条命令记录：参数、耗时、退出码、stderr 前 20 行 → 命令日志。
- 超时与取消：tokio `timeout` + `kill_on_drop`；大操作（clone/fetch）用流式输出。

## 5. 数据流：单写队列 + 增量刷新

### 5.1 单写队列（解决 90% 的"卡死/报错"）

所有**修改仓库状态**的操作进入串行队列：

```
用户点击 ──▶ OpQueue (tokio mpsc, 单消费者)
              ├─ 前置检查（中间态？冲突？保护分支？）
              ├─ 写恢复点（refs/grove/undo/<n>）
              ├─ 执行 git（流式输出）
              ├─ 更新内存模型（局部）
              └─ 广播 event: op-finished
```

- 并发写 = `index.lock` 冲突 = 用户眼里的"莫名其妙失败"。单队列从根上消灭它。
- 读操作（log/diff/show）**不进队列**，可并发，且永远不阻塞写。
- 队列可暂停/取消：长任务显示进度，可"在后台继续"。

### 5.2 增量刷新

```
watcher(fsevents) ──debounce 150ms──▶ 变更分类
   ├─ 工作区路径变化 ──▶ 只重算 status（--porcelain=v2，带 pathspec 限定）
   ├─ HEAD/refs 变化 ──▶ 只重算 refs + log 首页
   ├─ index 变化     ──▶ 只重算 status
   └─ 大变动（fetch/checkout）──▶ 全量失效，但分页重建
```

- 每个请求带 `generation` 序号，过期响应直接丢弃（避免"旧结果覆盖新结果"）。
- 前端 store 采用**结构共享**更新，只 patch 变化的行（zustand 选择器订阅），避免整树重渲染。
- 列表分页：首屏 300 条，滚动到 80% 预取下一页（`--skip`），后台补齐。

### 5.3 取消与背压

- 每个 IPC 调用携带 `requestId`，前端可取消；Rust 侧 `AbortHandle`。
- 快速切换分支时，取消上一个未完成的 log/diff 请求。
- 事件流节流：同一 16ms 帧内合并多次刷新。

## 6. 关键模块设计

### 6.1 提交图（Graph）

**输入**：`git log --topo-order --parents -n 500 --format=%H%x1f%P%x1f%an%x1f%ae%x1f%at%x1f%s%x1f%D`

**算法**（增量 lane 分配）：

```
active_lanes: Vec<Option<sha>>   // 每条 lane 期待的提交
for commit in commits:
    lane = active_lanes.position(commit.sha) ?? alloc_lane()
    edges = []
    for i, parent in commit.parents:
        target = (i == 0) ? lane : (active_lanes.position(parent) ?? alloc_lane())
        edges.push((lane, target, kind))
        active_lanes[target] = parent
    active_lanes[lane] = commit.parents.first()
    compact_empty_lanes()
```

- 复杂度 O(n · lanes)，1 万提交 < 20ms。
- 渲染：Canvas 2D，DPR 感知，绘制可视区 ± 1 屏；颜色按分支首次出现稳定分配。
- 折叠：已合并分支（`--merged`）默认淡化，lane 可压缩。

### 6.2 Diff 引擎

```
git diff/--cached/show ──▶ 原始 unified diff（行级）
        │
        ├─▶ similar::TextDiff (Patience) 重新对齐（更贴近人的直觉）
        ├─▶ 行内词级 diff（按 token 切分，空白不计）
        ├─▶ tree-sitter 高亮（两侧分别解析，按行偏移映射）
        └─▶ 结构化 rows: {kind: ctx|add|del, old_no, new_no, spans[]}
```

- 大文件：> 2MB 或 > 2 万行 → 只返回摘要 + "按需加载"。
- 二进制：不读内容，返回 size/hash/类型。
- 结果 LRU 缓存（key = blob 对 + 选项），容量 200 条。

### 6.3 交互式 rebase

1. `git log --reverse base..HEAD` 生成 todo 草稿；
2. 前端拖拽/改动作 → `{action, sha, message}` 列表；
3. Rust 写 `.git/grove/rebase-todo`，`GIT_SEQUENCE_EDITOR=<script>` 注入；
4. 执行 `git rebase -i base`，实时解析 stdout 进度（`Rebasing (2/5)`）；
5. 冲突 → 进入冲突中心，`git rebase --continue|--skip|--abort`；
6. 完成后对比 `ORIG_HEAD`，写入撤销记录。

边界：空提交（`--empty=drop`）、merge 提交（`--rebase-merges`）、签名、hooks 失败、autosquash。

### 6.4 冲突中心

- 解析 `git ls-files -u -z` → 每个文件 3 个 stage blob。
- 三方内容：`git merge-file --diff3 -p ours base theirs` 或按 stage 直接取。
- 结构化 resolver 插件化：

```rust
trait Resolver {
    fn matches(&self, path: &Path, content: &ThreeWay) -> bool;
    fn resolve(&self, path: &Path, content: &ThreeWay) -> Resolution; // Auto | NeedsHuman
    fn rationale(&self) -> String; // 展示给用户的依据
}
```

内置：Lockfile、Json/Yaml、ImportBlock、VersionLine、WhitespaceOnly、GeneratedFile。

- 每个 auto 结果带 `confidence` 与 `explain`，UI 明确标注"自动，可撤销"。
- 解决后 `git add`；全部完成 → 主按钮"继续"。

### 6.5 撤销（Undo）

```rust
struct JournalEntry {
    seq: u64,
    op: OpKind,            // commit / amend / branch_delete / reset ...
    at: DateTime,
    refs_before: Vec<(RefName, Oid)>,  // 只记变化前的 ref
    head_before: Oid,
    inverse: InverseOp,    // 执行过的反向指令（生成后即验证）
    undone: bool,
}
```

- 存储：`.git/grove/journal.jsonl`（append-only，滚动保留 500 条）。
- 恢复点：`git update-ref refs/grove/undo/<seq> <old-sha>`（对象不会被 gc）。
- 撤销时优先执行 `inverse`，失败则回退到 reflog 手工方案，并在 UI 说明。
- push / 远程变更类操作**标记为不可撤销**，只提示。

### 6.6 本地私有文件规则

- 配置：`.git/grove/local-only.json`

```json
{
  "version": 1,
  "patterns": ["*_test.php", "config/local.*", ".env.local", "**/docker-compose.override.yml"],
  "mode": "exclude-from-stage",
  "globalFallback": true
}
```

- 暂存时若路径命中 → 前端置灰并跳过；提交前做一次 `git diff --cached --name-only` 校验，命中则阻止并高亮。
- 只在 UI 层拦截，不改 `.gitignore`（避免影响团队）。

### 6.7 状态与错误归一化

把 git 的 stderr 映射为结构化错误：

```rust
enum GitError {
    NotARepo, Locked { path }, AuthRequired { remote }, NonFastForward { .. },
    LocalChanges { paths }, Unmerged { paths }, HookFailed { hook, output },
    Network { .. }, DiskFull, Unknown { cmd, stderr },
}
```

前端按类型渲染对应文案与操作按钮（见 [02 §8](02-产品设计.md#8-关键文案原则)）。

## 7. IPC 契约（节选）

```ts
// 命令
repo.open(path): RepoSnapshot
repo.status(): ChangeSet
repo.log({ ref, skip, limit }): { commits, graph, hasMore }
repo.diff({ kind: 'worktree'|'index'|'commit', path, commit }): FileDiff
repo.stage({ paths }): void
repo.stageHunk({ file, hunkIndex }): void
repo.commit({ message, amend, sign, push }): CommitResult
repo.push({ remote, branch, force? }): PushSummary
repo.run({ op: 'merge'|'rebase'|'cherry-pick'|..., args }): OpResult
repo.undo(seq?): UndoResult
conflict.resolve({ path, choices }): void
conflict.autoResolve({ paths }): Resolution[]

// 事件
event('repo:changed', { generation, scope })
event('op:progress', { opId, phase, done, total, message })
event('op:finished', { opId, ok, summary, undoSeq })
event('task:log', { opId, line })
```

类型由 Rust 侧 `serde` + `tauri-specta` 生成 TS，杜绝前后端字段漂移。

## 8. 安全与隐私

- 无遥测、无崩溃上报（可选、需显式同意、匿名、可查看内容）。
- 凭据：完全交给 `git credential` / Keychain，App 不落盘 token；OAuth 令牌存 Keychain（`kSecClassGenericPassword`，仅本机）。
- 命令执行：数组参数 + 路径校验，禁止 `sh -c`；工作区路径必须 `canonicalize` 且属于已打开仓库。
- 网络：仅用户显式操作时访问远端；支持系统代理与 `~/.ssh/config`。
- 权限：不做全盘访问；只请求用户选择的目录（security-scoped bookmark 记住）。

## 11. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| WebView 长列表卡顿 | 中 | 高 | Canvas + 虚拟化 + DOM 预算 + 提前压测 |
| git 版本差异导致解析失败 | 中 | 中 | 最低 2.30；版本探测；容错解析；CI 多版本测试 |
| rebase 边界情况多 | 高 | 中 | 先只支持 `-i` 常见动作；异常一律可 abort |
| 冲突 resolver 误判 | 中 | 高 | 只自动解决"可证明等价"的情况；全部可撤销 |
| 签名/公证流程卡住 | 中 | 中 | 提前申请账号；本地 ad-hoc 先自用 |
| 范围失控 | 高 | 高 | 每阶段 DoD；反功能清单；不做编辑器/终端 |
| 单人维护精力 | 高 | 高 | 内核与 UI 解耦；测试覆盖解析层；文档先行 |
