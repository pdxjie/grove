# 01 市场与痛点分析

> 结论先行：Git GUI 的功能早已过剩，稀缺的是**响应速度、操作可逆性、冲突出口**三件事。
> 这三件事恰好都是架构问题，不是功能问题——所以新入局者仍有机会。

---

## 1. 先定义用户：我们为谁做

不是"所有开发者"，而是下面这类人（也就是你本人）：

| 特征 | 说明 |
|------|------|
| 角色 | 独立开发者 / 小团队全栈，一个人维护多个仓库 |
| 日常 | 每天 10~50 次 commit，频繁切分支、rebase、处理冲突 |
| 仓库 | 中型偏大（1 万~20 万提交），偶有 monorepo、子模块、子目录多仓库 |
| 环境 | macOS，Apple Silicon，外接显示器，暗色模式 |
| 工具 | 终端 + IDE 内置 Git + 某个 GUI，三者来回切 |
| 痛点 | 等、怕、猜：等刷新、怕误操作、猜自己推了什么 |
| 付费意愿 | 一次性买断可以，订阅抗拒；讨厌账号墙和遥测 |

**非目标**：Git 零基础新手（那是 GitHub Desktop 的地盘）、需要企业审计/权限管控的大团队（那是 GitKraken/Tower 企业版的地盘）。

## 2. 竞品全景（2026）

> 价格与形态参考 2026-08 的公开信息，含竞品自述，需打折看待。

| 客户端 | 价格 | 技术形态 | 强项 | 致命短板 |
|--------|------|----------|------|----------|
| **GitHub Desktop** | 免费 | Electron | 极简、新手友好、GitHub 打通 | 无交互式 rebase、diff 弱、大仓库卡、实质 GitHub-only |
| **Fork** | $59.99 买断 | 原生 | 快、克制、日常手感好 | 小团队闭源、无 Linux、PR 只能创建不能审 |
| **Tower** | $69/年起 | 原生 | 最完整、撤销机制好、PR 管理 | 订阅制、贵、功能重 |
| **Sublime Merge** | $99 买断 | 自研 UI 框架 | 极致快、命令日志透明 | 几乎不迭代、无 PR、生态孤岛 |
| **GitKraken** | 免费档 + ~$10/月 | Electron | 图最漂亮、多平台、全家桶 | 重、必须账号、免费档限私有库 |
| **GitButler** | 免费（FSL→MIT） | Tauri + Rust | 虚拟分支、并行开发范式 | 范式迁移成本高、经典分支流用户用不上 |
| **Sourcetree** | 免费 | 原生 | 免费、Bitbucket 场景 | 架构老、大仓库卡顿、维护乏力、认证事故 |
| **lazygit / gitui** | 免费 | TUI | 键盘流极快、SSH 可用 | 无图形化 diff、无 forge 集成、学习曲线陡 |
| **GitWand** | 免费 | Tauri 2 + Rust | 冲突自动分类解决 | 新品、生态薄 |

来源：[The best Git GUI clients in 2026](https://github.com/devlint/gitwand/blob/77da7f82c6f89dab3aa67fdf6049f85a525c02e6/website/blog/best-git-gui-clients-2026.md)（作者为竞品开发者，观点需折算）、[Sourcetree 大仓库性能缺陷单](https://jira.atlassian.com/browse/SRCTREEWIN-14638)。

### 读表得出的三个事实

1. **快与全不可兼得**：快的（Sublime Merge）功能少；全的（Tower/GitKraken）重且贵；免费的（Sourcetree/GitHub Desktop）架构旧。
2. **审美断层**：好看的要么是 Electron（内存/启动代价），要么是十年前的视觉语言。
3. **冲突无人真正解决**：所有客户端都把冲突"漂亮地展示出来"，然后让你自己扛。这是全行业最大的未解问题。

## 3. "难用"的六类根因

用户说的"卡、鸡肋、不方便"，拆开是六个独立的工程问题：

### 3.1 刷新模型错了（卡的根因，占 70%）

典型实现：监听文件变化 → 全量 `git status` + 全量 `git log` → 重建整棵 DOM/列表 → 卡 1~3 秒 → 再触发一次监听（自杀式循环）。

- 大仓库 `git status` 本身就要 200ms~2s；
- 全量重绘 5 万行提交列表 = 主线程长任务；
- 网络 fetch 与本地刷新抢同一把锁，UI 直接假死。

**正确做法**：增量、分层、可取消。详见 [04 技术架构](04-技术架构.md#5-数据流单写队列--增量刷新)。

### 3.2 交互模型错了（鸡肋的根因）

- **点击路径太长**：暂存一个 hunk 要 4 次点击 + 2 次弹窗；rebase 要开新窗口。
- **没有键盘**：所有操作只能鼠标，重度用户一天点几千次。
- **模态弹窗成灾**：每个危险操作一个确认框，最后用户闭眼点"确定"，确认形同虚设。
- **没有命令面板**：功能藏在三级菜单里，找不到 = 不存在。

### 3.3 危险操作不可逆（怕的根因）

删分支、hard reset、force push、drop stash——多数客户端给一个红色弹窗就完事，**没有撤销**。Tower 靠"undo"建立口碑，说明这件事多稀缺。

真相是：Git 几乎什么都能恢复（reflog + `refs/` 快照），只是客户端不肯做。

### 3.4 冲突是死胡同（最痛）

冲突时用户面对：三个窗格 + 一堆 `<<<<<<<`，没有"这一步做完了吗"的进度感，没有"放弃这次 rebase"的明确出口，rebase 进行到一半关掉客户端，第二天不敢动仓库。

全行业默认：**冲突是用户的事**。但实测中大量 conflicted hunk 根本不需要决策（两边同样改动、仅顺序不同、锁文件版本号、import 排序）。

### 3.5 信息不透明（猜的根因）

- 推送前不知道到底推了哪几个提交、改了哪些文件；
- 不知道客户端背后跑了什么命令（出问题无法复现、无法学习）；
- 不知道当前仓库处于 merge/rebase/cherry-pick 哪个中间态。

### 3.6 平台与信任成本

强制账号（GitKraken）、遥测、订阅、云端同步仓库元数据——对"只想要个本地工具"的人是纯负担。

## 4. 空位在哪（2026 的机会窗口）

| 空位 | 说明 | 我们的对策 |
|------|------|-----------|
| **快 + 全 + 美 的交集** | 三者目前无人同时做到 | Rust 内核 + 增量渲染 + 自建设计系统 |
| **冲突的结构化解决** | GitWand 刚起步，其他家空白 | 冲突中心：能证明无需决策的自动解决，剩下的给人 |
| **操作可逆** | 仅 Tower 做好，且要订阅 | 全局撤销 + 操作日志，免费本地 |
| **推送前审查** | 几乎无人做 | "我将推送什么"预览 + 提交清单 |
| **中文 + 国产托管** | Fork/Tower 无中文，Gitee/Coding 支持为零 | 中文优先，GitHub/GitLab/Gitee/自建 GitLab 一等公民 |
| **无账号本地优先** | 大厂产品做不到（商业模型冲突） | 无账号、无遥测、离线全功能 |

**窗口期判断**：GitButler 证明了 Tauri + Rust 可以做 Git 工具且性能可接受；Rust 生态（gix、similar、tree-sitter）已成熟到可以自建高性能内核。现在做，技术风险最低。

## 5. 两次旧尝试的复盘

### 5.1 `source_tree`（Tauri 2 + Vue 3，约 2500 行）

**做对的**：技术选型（系统 git CLI 继承凭据/hooks/LFS）、rebase 序列器思路、提交图 lane 布局、性能意识。

**没走通的原因**：
1. 只有 PLAN，没有**产品定义**——功能清单是"竞品有什么"，不是"我每天要做什么"。
2. 没有性能预算与验收门槛，写完才发现大仓库仍卡。
3. UI 从零手搓 1263 行单文件 `App.vue`，没有设计系统，越写越难改。
4. 范围过大（P0~P3 一口气铺开），没有"可日用"的里程碑。

### 5.2 `idea-git-workbench`（IntelliJ 插件，功能相当完整）

**做对的**：真实痛点洞察——`*_test.php` 这类本地私有文件不该进提交；hunk 级回滚；冲突三选一快捷操作；中文文案。

**形态问题**：
1. 寄生 IDEA：启动慢、UI 受平台约束、非 Java 项目用不上、无法独立分发。
2. IDEA 自带 Git 已够用，插件是"第二套 UI"，价值感被稀释。
3. 无法做"好看"——这是平台天花板，不是实现问题。

### 5.3 这次怎么不一样

| 维度 | 旧尝试 | Grove |
|------|--------|-------|
| 起点 | 功能清单 | 5 个 JTBD 场景 + 性能预算 |
| 范围 | 一次铺满 | 每阶段一个"可日用"目标 |
| UI | 边写边凑 | 先定设计系统，再写组件 |
| 验收 | "能跑" | 量化指标（启动/打开/滚动/内存） |
| 形态 | IDE 插件 / 脚手架 | 独立 macOS App，可分发 |

## 6. 结论：楔子（Wedge）

不要做"又一个 Git 客户端"，要做**"大仓库 + 高频冲突 + 讨厌等待"人群的专用工具**。

第一版只承诺五件事，做到同类最好：

1. **打开就快**：10 万提交仓库 1 秒内可用。
2. **提交不慌**：hunk 级暂存 + 推送前预览 + 本地私有文件不提交。
3. **冲突有解**：能自动判定的自动解决，剩下的给清晰的三方界面与出口。
4. **手滑不怕**：⌘Z 撤销上一步，操作日志可复制可回放。
5. **找得到**：⌘K 命令面板，键盘全流程可达。

这五件事做完，才配谈 PR 集成、AI、插件生态。
