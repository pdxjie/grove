## 2. M0 · 地基与 Spike（第 1 周）

**目标**：把"会不会白干"的风险全部前置干掉。

### 任务

1. 初始化仓库结构（`core` / `app` / `docs`），CI（rust fmt+clippy、vitest、`pnpm build`）。
2. 5 个 Spike（见 [04 §10](04-技术架构.md#10-技术验证清单动手前先做-5-个-spike)），每个产出：结论 + 数据 + 是否阻塞。
3. 设计令牌落地为 CSS 变量 + 亮暗两套；做出"提交图 + diff"两张静态高保真样张。
4. IPC 骨架：`repo.open` / `repo.status` / `repo.log` / `repo.diff` 跑通，类型自动生成。

### DoD

- [ ] Spike 报告：20 万提交仓库的首屏耗时、内存、帧率均有数字
- [ ] `pnpm tauri dev` 打开后，1 秒内渲染 1000 条提交 + 选中后 200ms 内出 diff
- [ ] 设计样张评审通过（暗色优先）

### 砍掉的条件

若 Spike 1（大仓库图）或 Spike 2（大 diff）不达标，**暂停功能开发**，先解决渲染架构（Canvas/分片/WebGL）。

## 3. M1 · 可提交（第 2–4 周）

**范围**

- 仓库：打开、最近列表、克隆（HTTPS/SSH）、多标签、会话恢复
- 变更：status（porcelain v2）、文件树、文件级暂存/取消/丢弃、diff 查看（统一/并排）
- 提交：message 编辑、amend、模板、提交并推送
- 历史：分页列表、搜索（message/author/path）、提交详情、文件列表
- 分支：列表、切换、新建、删除、重命名
- 同步：fetch / pull / push，凭据走系统 helper，进度可见
- 基础框架：命令日志抽屉、Toast、错误归一化文案

**DoD**

- [ ] 在一个 3 万提交的真实仓库上，完成"改 3 个文件→只提交 2 个→推送"
- [ ] 切换分支 < 300ms，列表不闪白
- [ ] 所有错误都有中文人话文案（无裸 stderr）
- [ ] 命令日志能看到每一步实际执行的 git 命令

**Demo 脚本**：打开 MC 项目 → 改一个文件 → 看 diff → 勾选 → 提交 → 推送 → 看命令日志。

## 4. M2 · 可协作（第 5–7 周）

**范围**

- 提交图（lane 布局、ref 徽标、折叠、稳定配色）
- hunk / 行级暂存
- merge / rebase / cherry-pick / revert + 中间态横幅
- 冲突中心（三方视图、逐 hunk、进度、continue/skip/abort）
- 遴选（cherry-pick，含多选、-x、冲突继续/跳过/中止）
- 贮藏基础（创建 / 列表 / 预览 / apply / pop / drop / --keep-index）
- 交互式 rebase（拖拽排序、squash/fixup/reword/drop、结果预览）
- 全局撤销 + 恢复点
- 推送预览（outgoing commits、文件汇总、force 警示）
- 本地私有文件规则（提交清单）
- 命令面板 ⌘K + 核心快捷键

**DoD**

- [ ] 10 个提交的交互式 rebase，中途制造 2 个冲突，全部解决并完成，无残留状态
- [ ] 误删分支 → ⌘Z → 分支恢复，且提示来源
- [ ] 推送预览能准确列出 3 个待推提交与文件统计
- [ ] `*_test.php` 默认不被勾选，强行暂存时提交被阻止
- [ ] 冲突解决全程无需终端

**Demo 脚本**：把 5 个提交压成 2 个（含冲突）→ 解决 → 完成 → 误删分支 → 撤销 → 推送预览。

## 5. M3 · 可日用（第 8–9 周）

**范围**

- 贮藏进阶（--staged、按文件贮藏、从贮藏建分支、pop 冲突恢复）
- Reflog 浏览器 + "回到此状态"
- Worktree 管理、子模块查看/更新
- 文件历史、blame
- 多仓库工作区（分组、批量 fetch、状态灯）
- 结构化冲突解决（锁文件、JSON/YAML、import 块、生成文件）
- 提交信息 AI（默认关闭，优先本地/可配 OpenAI 兼容端点）
- PR/MR：GitHub / GitLab（列表、创建、检出、打开浏览器审查）
- 性能加固与内存泄漏排查

**DoD**

- [ ] 连续 7 天只用 Grove，记录每天"被迫回终端"的次数（目标 0）
- [ ] 空闲内存 < 180MB，10 万提交峰值 < 350MB
- [ ] 冲突中心对 `composer.lock` 能自动判定并给出依据，且可撤销
- [ ] 3 个仓库同时打开，切换标签 < 100ms

## 7. 每周节奏

| 时间 | 内容 |
|------|------|
| 周一 | 从 backlog 取 3 件事，写清 DoD |
| 周二–周四 | 实现，每天至少一次真机自用 |
| 周五 | 性能采样 + 修回归 + 更新文档 |
| 周日 | 30 分钟复盘：本周最卡的 3 个瞬间，进下周 backlog |

**规则**：任何新想法先写进 `backlog.md`，不打断当前里程碑。每个里程碑结束打 tag（`m0`…`m4`）。

---

## 8. 如果时间不够，砍什么

按"对'好用'的伤害"从小到大：

1. PR/MR 集成（打开浏览器也能用）
2. AI 提交信息
3. 子模块 / worktree 管理
4. blame（可用命令行）
5. 多仓库工作区（先支持多标签）
6. 结构化冲突 resolver（保留三方编辑器）

**绝不砍**：性能预算、撤销、冲突出口、命令面板、本地私有规则。这五样是产品存在理由。
