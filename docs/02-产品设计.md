# 02 产品设计

---

## 1. 定位

**Grove：为重度 Git 用户做的 macOS 客户端——快、可逆、冲突有解。**

- 对 Fork：更快、更美、冲突更强、中文原生。
- 对 Tower：不订阅、更轻、键盘优先。
- 对 GitKraken：不强制账号、不开 Electron。
- 对 GitHub Desktop：面向"已经会 Git 的人"，允许复杂操作。
- 对 GitButler：不改变你的分支心智模型，只把经典流程做到极致。

**三条产品原则**

1. **速度是功能，不是性能优化项。** 任何交互超过 100ms 都要有反馈，超过 300ms 必须有进度/可取消。
2. **默认安全，且可后悔。** 破坏性操作先写"恢复点"，再执行；撤销是一等公民。
3. **把 Git 的中间态变成一等公民。** merge/rebase/cherry-pick/revert 进行中，界面必须明确、可继续、可中止。

---

## 2. 目标用户与非目标

**目标**：每天写代码、已经懂 Git、被现有客户端拖慢的人。他们是"能看懂命令行，但不想敲"的人。

**非目标**：
- 完全不懂 Git 的新手（不隐藏概念，不简化到失真）；
- 需要集中管控/审计的企业（v1 不做 SSO、策略下发）；
- Windows/Linux 用户（架构预留，v1 只做 macOS）。

## 3. 五个核心场景（JTBD）

设计评审时，任何功能必须能挂到下面某个场景，否则砍掉。

### 场景 A：早上开工，先看"我昨天留下的烂摊子"

> 打开 App → 3 个仓库标签已恢复 → 当前仓库顶部横幅显示"rebase 进行中（2/5），2 个冲突"。
> 点"继续处理"直接进冲突中心，不用回忆昨天做到哪。

**要求**：会话恢复（标签、滚动位置、选中项）、仓库中间态检测、一键回到未完成的操作。

### 场景 B：改完一堆文件，挑着提交

> 工作区按目录树展示 → 勾掉 `config/local.php`、`*_test.php`（命中了"本地私有"规则，自动不勾选）→ 点开 diff，把调试用的 `var_dump` 那一个 hunk 取消 → 写提交信息（AI 建议 + 模板）→ ⌘Enter 提交 → 顺手"提交并推送"。

**要求**：文件/目录/hunk/行四级暂存；规则化"本地私有"；提交信息助手；提交前 diff 全览。

### 场景 C：推送前确认"我到底推了什么"

> 点推送 → 弹出推送预览：3 个提交、12 个文件、+340/−88，目标分支 `origin/main`，是否有 force 风险。
> 确认后推送，底部出现命令日志 `git push origin main`，可复制。

**要求**：outgoing 计算（`@{u}..HEAD`）、文件级汇总、保护分支提示、命令可见。

### 场景 D：把 5 个提交整理成 2 个

> 在历史里选中 5 个提交 → 右键"交互式 rebase" → 拖拽合并、改 message、丢掉一个 → 预览结果图 → 执行 → 冲突时原地进入冲突中心，逐条解决后自动 continue。

**要求**：可视化 rebase、结果预览、冲突内联处理、可中止回滚。

### 场景 E：手滑了

> 误删了分支 / 误 reset --hard / 误 drop stash → 顶部 Toast "已删除分支 feature/x [撤销]" 或 ⌘Z → 恢复，并提示"已通过 reflog 恢复"。

**要求**：操作日志、恢复点、撤销矩阵（见 §5.2）。

## 4. 功能地图

### P0 — 没有它就不是 Git 客户端（M1 完成）

- 打开/克隆仓库、最近仓库、多标签
- 工作区状态（porcelain v2）、文件树、文件级暂存/取消/丢弃
- Diff 查看（统一/并排、语法高亮、词级对比）
- 提交（含 amend、签名、模板）、提交并推送
- 历史列表（分页、搜索、作者/路径过滤）、提交详情
- 分支列表、切换、新建、删除、重命名
- fetch / pull / push（含凭据、进度、错误可读化）

### P1 — 让它"好用"（M2 完成）

- hunk / 行级暂存（文件级已在 P0）
- 提交图（lane 布局、合并/分叉、ref 徽标、折叠）
- 合并 / rebase（普通）/ 遴选（cherry-pick）/ revert，冲突中心
- 贮藏基础：创建（含 --keep-index / 仅暂存 / 含未跟踪）、列表、预览、apply/pop/drop
- 交互式 rebase（可视化 todo）
- 全局撤销 + 操作日志
- "我将推送什么"预览
- 本地私有文件规则（提交清单）
- 命令面板 ⌘K + 完整快捷键

### P2 — 让它"强大"（M3 完成）

- 贮藏进阶：仅贮藏指定文件、从贮藏建分支、pop 冲突恢复
- Reflog 浏览器、"回到某个状态"
- Worktree 管理
- 子模块查看与更新
- 文件历史 / blame（行级作者）
- 多仓库工作区（分组、批量 fetch）
- 结构化冲突解决（锁文件、JSON/YAML、import 块）
- 提交信息 AI（本地模型可选，默认关闭）
- PR/MR：GitHub / GitLab / Gitee 的列表、创建、检出、简单审查

### P3 — 生态（v1.1+）

- 主题系统、密度、字体自定义
- CLI 伴侣（`grove .` 打开当前目录）
- 插件/脚本钩子
- Linux/Windows 移植（Tauri 架构天然支持）

### 反功能清单（明确不做）

| 不做 | 理由 |
|------|------|
| 内置代码编辑器 | 编辑器是 IDE 的事，做不好还拖慢启动 |
| 内置终端（v1） | 与"命令日志"重复；v2 可考虑只读日志 + 单条重跑 |
| 账号体系 / 云同步 | 与"无账号"原则冲突 |
| 强制 AI | 默认关闭，且优先本地模型 |
| 自动 commit / 自动 rebase 机器人 | 不可控，破坏信任 |
| 花哨的 Git Flow 按钮 | 概念过时，遮蔽真实分支操作 |

## 5. 六个差异点（详细设计）

### 5.1 极速内核（贯穿全局）

不是"优化"，是**架构约束**。见 [04 技术架构 §4.4](04-技术架构.md)。产品侧体现：

- 打开仓库时先渲染骨架（分支名 + 最近 30 条），1 秒内可交互，其余后台补齐；
- 任何列表滚动不出现白屏；
- 网络操作永远不阻塞本地操作（fetch 时照常 commit）；
- 长任务（clone、gc、大 fetch）进"任务中心"，可后台、可取消。

### 5.2 全局撤销 + 操作日志

**恢复点机制**：每次写操作前，向 `refs/grove/undo/<seq>` 写入当前 HEAD 与涉及分支的旧值（轻量，不复制对象）。

**撤销矩阵**：

| 操作 | 撤销方式 | 提示语 |
|------|----------|--------|
| commit | `reset --soft HEAD@{1}` | 已撤销提交，改动回到暂存区 |
| amend | 恢复原提交对象 | 已恢复修改前的提交 |
| 分支删除 | 重建 ref 指向旧 sha | 已恢复分支 feature/x |
| reset --hard | 重置回旧 sha（工作区丢失部分提示） | 已恢复，丢弃的工作区改动无法找回 |
| 合并/变基完成 | 回退到操作前 sha | 已撤销合并 |
| stash drop | 从 reflog 恢复 stash 对象 | 已恢复贮藏 |
| 暂存/取消暂存 | 反向操作 | 静默 |
| push | **不可撤销**（只提示） | 已推送，如需回退请 force push（不提供） |

UI：Toast 内嵌"撤销"按钮，5 秒内有效；命令面板 `Undo Last Operation` 永久可达（基于 reflog，最多回溯 50 步）。

**命令日志**：底部抽屉，记录每条执行的 git 命令、耗时、退出码、输出摘要。可复制、可展开全文、可"在终端重跑"。这是"透明"原则的落地，也是排障入口。

### 5.3 冲突中心（核心差异化）

触发条件：仓库处于 merge / rebase / cherry-pick / revert / amd 中间态。

**布局**：全窗口接管（不弹窗），三栏 + 底部进度。

```
┌──────────────────────────────────────────────────────────┐
│ ⚠ 变基进行中 2/5 · 2 个冲突  [继续] [跳过] [中止并回滚]   │
├────────────┬───────────────────────────┬─────────────────┤
│ 冲突文件 2 │  Ours │ Base │ Theirs      │ 结果预览        │
│ src/A.php  │  ... 三方对照，hunk 可点选  │ 合并后的结果     │
│ src/B.php  │                           │                 │
├────────────┴───────────────────────────┴─────────────────┤
│ 建议：hunk #1 两侧改动等价，可自动采用 Theirs  [采纳建议] │
└──────────────────────────────────────────────────────────┘
```

**结构化解决（"能证明无需决策"）**：

| 类型 | 策略 |
|------|------|
| 锁文件（package-lock.json / composer.lock / pnpm-lock.yaml） | 不手工合并：标记冲突 → 采用一侧 → 提示"重新生成"（可配置命令） |
| JSON / YAML / TOML | 按键路径三方合并，数组按 id 去重合并 |
| import / use 语句块 | 集合并集 + 排序去重 |
| 版本号、时间戳行 | 取较高版本/较新时间，标注 |
| 纯格式化差异（空白/换行） | 忽略空白后若无差异，自动通过 |
| 生成文件（dist、build） | 提示"应由构建产物替代"，不进入冲突队列 |

每条自动决策都带**依据**（"两侧内容相同，仅行序不同"）与**可撤销**，绝不静默。

**进度感**：文件列表打勾、剩余数、当前第几个 hunk；全部解决后主按钮变"继续变基"。

**出口**：任何时刻可"中止并回滚"（`rebase --abort` / `merge --abort`），且回滚也进撤销栈。

### 5.4 提交前审查：提交清单 + 推送预览

**提交清单（本地私有不提交）**

沿用 `idea-git-workbench` 验证过的痛点：`*_test.php`、`config/local.*`、`.env.local` 这类文件天天改、永远不该提交。

- 规则存在 `.git/grove/local-only.json`（不进工作区，不污染仓库）；
- 支持通配符、按目录、按仓库/全局两级；
- 命中的文件在变更列表灰色显示，默认不勾选，顶部提示"3 个本地私有文件未纳入提交"；
- 提交时二次校验：若暂存区仍含命中文件，阻止并高亮。

> 完整的暂存/提交/遴选/贮藏语义见 [06 暂存区与操作语义](06-暂存区与操作语义.md)。

**推送预览**：列出 `upstream..HEAD` 的提交（sha、message、作者、时间）、文件汇总、增删行数、目标远端/分支；若需要 force，红色警示并说明后果。

### 5.5 命令面板 + 键盘优先

- ⌘K 打开，模糊搜索所有命令（含"打开仓库""切换分支""交互式 rebase"）；
- 命令显示快捷键，回车执行，支持最近使用；
- 导航：`j/k` 上下、`h/l` 折叠/展开、`空格` 暂存、`⌘Enter` 提交、`⌘⇧P` 推送、`g h` 历史、`g c` 变更；
- 所有快捷键可在设置里改，且可导出为 cheatsheet。

### 5.6 多仓库工作区

- 标签页（⌘1..9 切换），每个仓库保留独立上下文（当前视图、滚动位置、选中提交）；
- 侧栏按"收藏 / 最近 / 分组"组织；
- 工作区（Workspace）：把一组仓库打包（如 ERP 的 api + web + docker），一键全部 fetch、查看各自状态；
- 全局状态灯：每个标签显示分支名 + 脏/净 + ahead/behind 数字。

## 7. 仓库操作状态机

任何时刻，仓库处于以下之一。顶部横幅必须明确显示，并提供对应出口。

```
clean ──commit──▶ clean
  │
  ├──merge──▶ merging ──┬─ all resolved ─▶ commit ─▶ clean
  │                     ├─ abort ─▶ clean
  │
  ├──rebase──▶ rebasing ─┬─ continue ─▶ clean
  │                      ├─ skip ─▶ rebasing
  │                      ├─ abort ─▶ clean
  │
  ├──cherry-pick──▶ picking ──┬─ continue ─▶ clean
  │                           └─ abort ─▶ clean
  │
  ├──revert──▶ reverting ──（同上）
  │
  └──conflict──▶ conflicted ──（必须进入冲突中心）
```

检测方式：`.git/MERGE_HEAD`、`.git/rebase-merge|rebase-apply`、`.git/CHERRY_PICK_HEAD`、`.git/REVERT_HEAD`、`git status` 冲突标记。

**离开中间态前不允许切换分支、不允许开始新的 merge/rebase**——按钮置灰并说明原因（多数客户端的"莫名其妙报错"就来自这里）。

## 8. 关键文案原则

- 错误信息必须包含：**发生了什么 + 为什么 + 怎么办**。禁止直接抛 git stderr。
  - 反例：`error: Your local changes to the following files would be overwritten by merge`
  - 正例："合并被阻止：`src/A.php` 有未提交改动。先暂存，或丢弃改动后再合并。" + [暂存] [丢弃] 按钮
- 危险操作不用"确定/取消"，用动词："删除分支" / "保留分支"。
- 中间态横幅永远给三个动作：继续、跳过（若适用）、中止。

## 9. 成功标准（v1）

- 我能连续 7 天只用 Grove 完成全部 Git 操作（不打开终端），且不觉得憋屈。
- 打开 10 万提交仓库到可交互 ≤ 1s，日常操作无一次超过 300ms 的等待。
- 冲突解决平均耗时比命令行快 30% 以上（自测 10 次有冲突的 rebase）。
- 新用户（会 Git 的同事）在无说明情况下 10 分钟内完成"打开仓库→改文件→提交→推送"。
